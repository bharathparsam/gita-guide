# Phase 1 architecture and production gates

## Scope

Phase 1 accepts one user message, validates it, applies local and NVIDIA input
safety, and classifies it with JEV. Retrieval and response generation are separate
stages and cannot weaken this boundary.

## Request flow

```text
HTTP ingress
  -> trusted UUID request_id + optional client_request_id
  -> authentication + byte/shape/length validation
  -> local crisis and explicit-language policy
  -> NVIDIA input safety
  -> idempotency claim
  -> exact classification-cache lookup
  -> process-local single flight
  -> JEV with bounded retry and circuit breaker
  -> strict ClassificationResult validation
  -> eligible-result cache write
  -> append-only audit + metrics + LangSmith trace
  -> response with X-Request-ID
```

The cache is intentionally behind both safety rails. Semantic caching is excluded
because nearby sentences can express materially different emotions or risks.

## Identity and traceability

- `request_id`: server-generated UUID used across logs, audits, and LangSmith metadata.
- `client_request_id`: separately validated caller correlation value; never trusted as the internal ID.
- `provider_request_id`: OpenRouter's identifier for the JEV decision.
- LangSmith trace/run IDs: generated by LangSmith and searchable using `request_id` metadata.
- `Idempotency-Key`: validated retry identity; scoped with tenant and HMAC-protected payload fingerprint.

## Data handling

- Application logs are JSON and exclude raw prompt text by default.
- Prompt correlation uses HMAC-SHA256 with a rotation key ID, not a plain hash.
- Audit records reject raw prompt, message, response, credential, and token fields.
- Cache and idempotency keys are HMACs; Redis never receives raw text as a key.
- Upstash REST values are base64 transport-encoded, not application-encrypted.
- LangSmith may receive runnable inputs and outputs when tracing is enabled. Production
  use requires approved retention, access, consent, and redaction controls.

## Failure policy

| Failure | Behavior |
|---|---|
| Local or NVIDIA safety block | Stop before cache and JEV; return sanitized 422 |
| Self-harm escalation | Stop before cache and JEV; return dedicated sanitized 422 |
| Required NVIDIA unavailable | Fail closed with 503 |
| JEV transient connection failure | Bounded retry with jitter |
| Repeated provider failure | Circuit opens; fail fast until recovery probe |
| Invalid JEV response | Reject; never cache |
| Low-confidence classification | Return `needs_review`; never cache |
| Cache corruption | Delete atomically and treat as a miss |
| Idempotency conflict | Return 409 without provider call |
| Audit persistence failure | Fail the request rather than claim an unaudited success |

## Production readiness gates

Code-complete is not the same as production-ready. Deployment approval requires:

1. Upstash TLS/auth, persistence, eviction, usage limits, backup, and failover verified.
2. Production secrets stored outside `.env` and rotation tested.
3. NVIDIA and OpenRouter data-handling agreements approved.
4. LangSmith sampling, retention, access, and deletion controls approved.
5. Rate limiting and tenant authentication implemented at the gateway.
6. Classification evaluation thresholds enforced in CI against a held-out dataset.
7. Load, soak, cache-stampede, Redis-failure, and provider-failure tests pass.
8. Dashboards and paging alerts validated in the target environment.
9. Human-review handling for `needs_review` and safety escalation is operational.
10. Privacy, threat-model, dependency, and incident-response reviews are signed off.

## Retrieval entry criteria

The retrieval implementation verifies embedding provenance and preserves verse
citation metadata. Before it enters the public request path, it needs a labeled
retrieval dataset and thresholds for recall@k, MRR, citation coverage, minimum
relevance, and abstention behavior.
